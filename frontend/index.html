A text language for microservice architectures

Architecture diagrams as text, with request flows you can play.

Write down your services, databases and queues once, the way you would in a design doc. Proschi draws the diagram as you type. Then describe each use case step by step, with real payloads and status codes: the happy path and every way it can fail. Press Play to watch the request move through the system, one scenario at a time.

01

How it works

  1. 1.1 Write the architecture

    One line per node: an id, a display name, a tech stack in brackets and an owning team. Groups draw a boundary around what they contain. Connections are arrows with an optional label.

    The editor autocompletes 108 tech stacks (AWS, GCP and Azure services, databases, queues, caches) and underlines mistakes as you type. 

    group vpc "AWS VPC" {
  gateway "API Gateway"   [AWS API Gateway] @platform
  orders  "Order Service" [REST API]        @orders
}
ordersDb "Orders DB" [PostgreSQL] @orders

gateway -> orders   : HTTP
orders  -> ordersDb : SQL
orders  -> events   : publish

  2. 1.2 Describe a use case

    A use case is a request flow, written as a sequence of steps. -> is a synchronous request, ->> is fire-and-forget, --> answers the last open request. Steps carry an HTTP method and path, a JSON, XML or text payload, and a status code. Steps inside par { } run in parallel. 

    usecase "Create order" {
  gateway -> orders : POST /api/orders json {
    "userId": "user123",
    "items": [{ "productId": "prod-1", "quantity": 2 }]
  }
  par {
    orders  -> ordersDb : INSERT order
    orders ->> events   : OrderCreated {"orderId": "order-789"}
  }
  orders --> gateway : 201 {"status": "pending"}
}

  3. 1.3 Branch into scenarios

    One endpoint rarely has one outcome. Inside a use case, alt "Name" { } blocks that follow each other are alternatives: each one becomes its own scenario, and the steps before them are written once and shared. Steps after the blocks are shared again by every branch.

    when "…" says why a branch happens, and paths may name their variable parts, as in /orders/{id}. -x is a call that never gets an answer: a timeout or a refused connection. Scenarios whose entry request ends in a 4xx or 5xx, or fails, are marked as error paths. 

    usecase "Get order" {
  gateway -> orders : GET /api/orders/{id}

  alt "Found" {
    orders  -> ordersDb : SELECT order
    orders --> gateway  : 200 {"id": 42, "status": "paid"}
  } alt "Not found" when "no order has this id" {
    orders  -> ordersDb : SELECT order
    orders --> gateway  : 404 {"error": "not_found"}
  } alt "DB timeout" {
    orders  -x ordersDb : SELECT order
    orders --> gateway  : 504
  }
}

  4. 1.4 Press Play

    Playback animates the use case over the architecture, one step at a time, and shows the request and response payload of each step. Tabs above the diagram switch between scenarios; services a scenario never touches fade out, and error responses and failed calls turn red.

    The use case picker groups use cases by the endpoint they start with, so everything about POST /api/orders sits together. It is a quick way to check that a flow actually touches the services you think it does, or to walk a new team member through the edge cases.

    Step 1
    gateway → orders POST /api/orders
    Step 2
    orders → ordersDb INSERT order parallel
    Step 3
    orders ⇢ events OrderCreated async
    Reply
    orders → gateway 201 {"status": "pending"}
    Alt
    “Not found” orders → gateway 404 error
    Alt
    “DB timeout” orders ✕ ordersDb no answer failed

  5. 1.5 Share a link

    The whole document is compressed into the URL, after #code=. A link can also point at a specific step of a use case and scenario, so it opens straight into playback there: handy for a bug report that says “this is the error path I mean”. The fragment never reaches a server; there is no server. 

    https://gvart.github.io/proschi/app/#code=C4S2BsFMAICIGEAWkDGBrA9gV2LAUHgO…&uc=place-order&alt=out-of-stock&step=2

02

The rest of it

Proschi features
Text first The text is the source of truth. Dragging a node on the canvas writes pos x,y back into it, double-click renames, dragging between two nodes adds a -> b. Auto-layout (ELK) places everything without a position.
Scenarios The architecture is written once; any number of use cases play over it. alt branches give one use case its success and error paths without copying the shared steps, and the use case picker groups use cases by endpoint.
Editors Keep .proschi files next to your code, split across files with import "infra.proschi". A VS Code extension with a live preview, a language server for IntelliJ, Neovim and others, and the proschi command (check, fmt, render to SVG or Markdown, and checks against your OpenAPI specs) all run the same parser as this editor. Editor setup.
Storage Saved diagrams live in your browser's local storage. Nothing is sent anywhere, and there is no tracking.
Files Download and open plain-text .proschi files, so diagrams can sit in a repository next to the code they describe.
Export PNG or SVG of the current diagram, or Mermaid text for the architecture or a scenario, ready to paste into a GitHub README.
Errors The parser never stops at the first problem. Each error has a line and column, and everything else still renders.
Source Free and open source. Source on GitHub.

03

Practice system design

Like LeetCode, for system design. Each problem gives you use cases, traffic and requirements; you design the system in Proschi and press Run tests. The simulation checks latency under load, availability when any node fails, durability and cost, and flow tests check the key idea, each with the measured value and a hint when it fails. Everything runs in your browser.
